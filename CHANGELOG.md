### Added

- Safer label tooling (#143–#146): P1 now means only a confirmed calculation bug, and P2 covers release blockers and other material defects. Label reconciliation runs only from `main`, also on manual dispatch. Before any change it checks every label it would prune against open and closed issues and pull requests and stops, changing nothing, if one is in use or cannot be queried. The sync and drift summaries render manifest and API values through a shared helper (`.github/scripts/markdown.mjs`) whose code spans cannot be closed by a backtick. Self-tests and `tools/quality_test_labels.py` cover each control.
- Verifiable bug and documentation reports (#141, #142): the bug form requires the host environment, acceptance criteria and validation, and the documentation form requires the location, problem, proposed correction, supporting source, acceptance criteria and validation. `tools/check_config.py` rejects a form that does not require its listed fields.
- Operational guides as current rules in my own voice (#124): `CONTRIBUTING.md`, `RELEASING.md`, `SECURITY.md`, `INSTALLATION.md`, `docs/GOVERNANCE.md`, `docs/TRAFFIC.md` and the tooling guide state the current rules in the first person and address contributors directly; dated history and references to past issues are left to the changelog, the issues and the provenance record. `SECURITY.md` now says that main holds the VBA modules. `python tools/check.py` rejects "the owner" and "the maintainer" in the operational guides. Specifications and decision registers are unchanged.
- Repository settings as code (#119): `docs/repository-settings.json` holds the general settings, security features and four managed rulesets (`main`, `release/**`, `v*` tags, `traffic-history`); `tools/setup_repository.py` previews, applies or checks them read-only with a dated evidence record, unit-tested offline. The tag ruleset is part of the baseline now. `docs/REPOSITORY_SETTINGS.md` explains the rules and points to the JSON. `docs/provenance.json` records the files adapted from my template.
- Pull-request issue links and final-head review (#122): the PR template asks for `Resolves #` on task PRs and `Refs #` on integration and sync PRs, and for a final-head review record (final head SHA, reviewed SHA, review result, CI run) renewed after any push; `docs/GOVERNANCE.md` states the same rule.
- Issue triage without default metadata (#121): the metadata workflow no longer adds or changes a priority, and gives an issue without a milestone the open milestone with the earliest due date after today, failing clearly when there is none; `ISSUE_MILESTONE_NUMBER` is no longer read. The read-only *Issue triage* workflow (`tools/check_issues.py`, unit-tested) reports issues without exactly one priority, with P1 off a bug, without an open milestone, a target end date before its due date or a dependency section, with unknown labels, or with `blocked` out of line with their prerequisites. The issue forms ask for the dependencies and a target end date.
- Traffic collection with a GitHub App token and tested code (#120): `Daily traffic export` reads the traffic API with a short-lived installation token from a dedicated App (Administration: read only; `TRAFFIC_APP_CLIENT_ID` and `TRAFFIC_APP_PRIVATE_KEY` in the `analytics` environment) instead of the `TRAFFIC_TOKEN` personal access token. Its Python moved from two heredocs into `tools/traffic_history.py`, unit-tested for merging, same-day replay, stale and invalid data, badges and alerts, and byte-identical to the old output on the live history. Collection (`contents: write`, with the environment) and alerting (`issues: write`, without it) are separate jobs; the schedule is 06:23 UTC; clones are no longer an alert reason.
- Release-file checks (#123): `tools/check_changelog.py`, run in CI with this repository's name and unit-tested under `python tools/check.py`, requires `## [Unreleased]` first, release headings `## [X.Y.Z] - YYYY-MM-DD` with real dates, newest first, a `/releases/tag/vX.Y.Z` link reference for each release and every link reference in this repository, and `VERSION` only from the first release, equal to the newest one. The changelog gains its `[Unreleased]` link reference. Dependabot's `target-branch` is now the one place that names the active release branch: every entry must name the same `release/X.Y.Z`, and CI fails if it does not exist; `ACTIVE_RELEASE_BRANCH` is gone.
- Scanning and hygiene workflows (#118): *CodeQL* analyses Python, Actions and the JavaScript label scripts with the `security-extended` suite on pushes and pull requests to `main` and `release/**` and weekly; pull requests run a read-only job that uploads nothing and keeps the SARIF as a 30-day artifact. *Link check* requests every external Markdown link weekly through the new `tools/check_links.py`, which also checks relative links and anchors offline in `python tools/check.py`. *Keep milestones issue-only* removes milestones from pull requests on pull-request events and in a daily scan, without running pull-request code.

The configuration checks reject a requirement without a pin and hash, a `pip install` without those flags, and a Dependabot configuration without the `pip` entry.
